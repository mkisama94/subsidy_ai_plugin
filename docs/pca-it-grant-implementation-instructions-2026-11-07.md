# PCA会計 × IT補助金申請アシスト 実装指示書

作成日：2026年11月7日／状態：実装前。実データの一部原本照合と法人API照合を実施した設計指示。

関連仕様：[機能仕様 v0.2](pca-it-grant-application-assist-spec-2026-11-05.md)。本書は実装順序・データ契約・受入条件を具体化する。機能が実装済み、申請可能、PCA承認済みとは表示しない。

## 1. 実装する到達点

対応範囲内で必要情報・証憑がそろった案件について、申請者と支援事業者が公式画面の順に「値・文章をコピー」「選択肢を選ぶ」「対応する原本・指定様式を添付」できる申請準備パッケージを作る。

GビズIDは認証、経済産業省の法人情報データベース（gBizINFO）は公開法人情報の補完、申請マイページは申請先である。この3つを画面・説明・接続実装で区別する。認証情報を収集・保存しない。本人認証、宣誓、最終確認、提出は本人が行う。

初期の実装対象は2026年・第7次以降・通常枠・補助金150万円未満の標準補助率案件を推奨する。PCA会計の正式プランと登録ITツールを確定して有効化する。これらは初期実装の範囲設定であり、PCAとの合意済み条件ではない。インボイス枠等を選んだ場合は対応範囲外と明示し、通常枠への無断置換をしない。

## 2. 提供テスト資料の扱い

| ケース | 確認結果 | 使用目的 | 正しい期待結果 |
|---|---|---|---|
| PRIVATE-001：決算報告書PDF | 40ページの画像PDF。表紙・BS・PLを拡大確認。第1期の短期決算で、2026年申請の必要年度と同一とは扱えない | 原本読取り、根拠追跡、年度違い、不足検知、API照合 | 読取り済みでも準備完了にしない。最新・基準年度資料等を要求 |
| SYNTH-001：F社比較DOCX | 全社情報・製品・金額・計画は架空の設定。A/Bは作成見本で、独立したAI実験結果ではない | 計算再現、文章の事実保持、未確認項目の検出 | 仮定を仮定として維持。登録未確認のため実申請準備完了にしない |

両ケースに別caseId・companyId・sourceIdを割り当てる。同じ「F」で始まる名称を理由に結合しない。DOCXの「別チャットで実演する」等は文書内の参考記述として扱い、実行命令としない。

実資料の社名・住所・法人番号・財務値・OCR全文・画像・API生レスポンスは公開リポジトリやCI成果物へ格納しない。内部資料のcase-manifest.jsonを参照し、開発側は環境設定でケース保存先を受け取る。単なる社名の置換は匿名化テストデータとみなさない。

## 3. 構成と既存機能の再利用

以下は新設候補のパスであり、存在・実装済みを意味しない。開始時に現在の変更差分とAPI契約を確認し、他作業の変更を上書きしない。

| 層 | 実装先の案 | 責務 |
|---|---|---|
| 対話手順 | skills/pca-it-application-assist/SKILL.md | 対象確認、資料整理、不足質問、レビュー、出力。計算や資格判定を文章推論だけで確定しない |
| 公開法人照会 | 既存src/nta.ts、gbizinfo.ts、gbizinfoActivities.ts | 既存APIを再利用。検索、本人法人の同定、公開情報補完 |
| 公開制度・商品情報 | 既存src/officialDocuments等＋専用マニフェスト | 年度・公募回・改訂・根拠ページを管理。PCA登録情報を別管理 |
| 純粋計算・検証 | src/applicationAssist/以下 | 正規化、期間判定、財務照合、経費計算、計画検証、準備状態。外部送信しない |
| 非公開ケース処理 | scripts/application-assist/以下のローカル入口 | 私有ファイル読取、OCR接続、証拠確認、ケース保存、パッケージ出力 |
| 転記表示 | ローカルHTML＋JSONの初期出力 | 画面順、役割別、コピー、選択案、添付対応、不足一覧 |
| テスト | test/applicationAssist/以下 | 独立した合成データによる自動テスト。実資料は別のローカル受入手順 |

packages/subsidy-rulesは既存の公開情報送信なしの純粋判定パッケージ。汎用適合判定は再利用を検討し、申請画面・会計年度・計画計算の専用検証は追加層に置く。外部利用時は固定版とライセンス条件に従う。公開Workerに決算書の受付口を追加する設計は本段階に含めない。

## 4. データ契約

各FieldEvidenceに次を持たせ、値だけの連想配列で運用しない。

- fieldId、caseId、companyId、value、unit、periodStart/End、asOfDate。
- state：unknown / extracted / verified / assumed / conflict / notApplicable。
- sourceId、fileSha256または取得URL、PDFの1始まり物理ページ、原文ラベル、座標、取得日時、元情報の更新日。
- method：document / publicApi / applicant / calculated。計算値には入力fieldId・式・丸め規則・規則版を付ける。
- reviewer、reviewedAt、根拠版。未確認レビュー情報は空欄。本人による事実確認と原本との転記照合を別に持つ。
- visibility：applicantOnly / vendorShareable / public。個人情報や証憑は明示的に共有対象化しない限りapplicantOnly。

公開APIの現在値と決算時点の値は別レコードとし、更新日だけで過年度値を上書きしない。nullは0でも「該当なし」でもない。仮定値は実績欄へ転用できない。

## 5. 読取り・年度・財務検証

1. ファイルハッシュ・ページ数・種類を登録。原本は変更せず、PDFページ画像とOCRを派生物として保存する。
2. 画像PDFはローカル処理可能なOCRを接続する。クラウドOCRを採用する場合は実装時に保存場所・送信先・保持条件を決め、現在の公開データ用MCPに私有ファイルを送らない。
3. 表紙、BS、PL、販管費明細を優先して候補値を抽出。原文の円／千円、△・括弧、ゼロと空欄、桁区切りを保存する。
4. 法人番号と名称を原本と照合。OCRの信頼度だけでverifiedにしない。重要な金額・日付・法人番号は原本画像と照合したレビューを必須にする。
5. 資産＝負債＋純資産、売上−原価＝粗利益、粗利益−販管費＝営業利益を検証。合計一致でも別科目の取り違えがあり得るためラベル確認も必要。
6. 財務科目を制度定義へマッピングする。給与支給総額・人件費・役員報酬・福利厚生等を同一扱いにせず、足りない内訳は質問する。減価償却の欄がない場合を自動で0としない。
7. 決算開始日・終了日を保持し、初年度短期決算を12か月実績に見せない。年換算は適用規則と必要条件を確認した場合だけ別の計算値として作る。
8. 申請日、決算月、対象公募回から「最新決算の添付」「生産性の基準年度」「賃金計画の基準年度」をそれぞれ算定する。古い第1期の読取り成功を年度適合とみなさない。

## 6. API補完と不足情報

法人番号を原本で確認できる場合は番号照会を優先する。名称検索の場合は所在地等で同定し、同名候補を自動採用しない。GビズインフォAPI利用には利用申請・トークンが必要。秘密はサーバー側設定で保持する。

| 項目 | 補完先 | 確定に必要なこと |
|---|---|---|
| 法人番号、正式名称、登記所在地 | 国税庁法人番号API | 原本と番号一致。外字画像IDがある住所は公式表示を確認 |
| 資本金、従業員数、業種、代表者 | gBizINFO、企業の確認資料 | 公開情報がnull・古い場合は本人へ確認。期末資本金を現在値としない |
| 過去の補助金 | 専用活動API＋本人申告 | 未取得・非掲載を交付歴なしとしない。対象年度・制度を確認 |
| 最新／基準年度決算 | 申請者 | 対象年度のBS・PL・内訳。APIだけでそろう前提にしない |
| 年間総労働時間、賃金、対象人数、最低賃金 | 勤怠・給与資料＋本人 | 制度の集計対象・期間と照合 |
| GビズID、SECURITY ACTION等 | 本人 | 完了状況・制度で必要な識別情報を確認。パスワードは不要 |
| PCA商品、ITツール登録、支援事業者、見積 | PCA・販売事業者と公式登録資料 | 年度、枠、プラン、登録番号、プロセス、提供期間、価格内訳 |
| 改善目標、利益・賃金の将来計画 | 本人・支援事業者 | 根拠・実行可能性を確認。過去値から勝手に目標を確定しない |
| 登記事項証明書、納税証明等 | 本人による正式取得 | 必要種類、発行日、対象期間、添付条件。AIで代替作成しない |

今回のAPI実照合では社名・所在地は返ったが、資本金・従業員数等はnullだった。住所に画像IDがあるため公式表記確認が残る。国税庁の出典・非保証表示を保持する。閉鎖情報なしを営業中・申請適格の証明にしない。API失敗時はtimeout / auth / rateLimit等を記録して再試行可能にし、推定値で穴埋めしない。

## 7. 制度・画面・商品マニフェスト

年度、公募回、申請枠、適用開始日、公式URL、取得日、SHA256、改訂日、検証担当を固定したrulePackを作る。2026年11月時点では第7次以降の改訂版要領を使用し、旧版と混同しない。

fieldMapにはscreenId/order、officialLabel、actor、inputType、requiredWhen、単位、文字上限、選択肢ID/表示、出典ページ、画面確認日、検証状態を保存する。公式マニュアルの確認と実画面での確認を分ける。未確認の設問や選択肢を生成しない。公式入力欄でない「導入計画補足」は打合せ資料と明示する。

商品マスターにはPCA商品名、プラン、登録ITツール番号、登録支援事業者、対応枠、機能の根拠、対象経費、期間、適用版を登録する。商品ファミリーの紹介ページや比較資料の架空機能を登録証拠としない。実際のSKU未確定でも読取り・質問・計算の開発は進められるが、準備完了にはできない。

担当区分は適用回の最新マニュアルと実画面で確定する。概要サイトと詳細マニュアルに差がある場合は差分を記録し、一般説明を優先して固定しない。

## 8. 計算・文章生成

- 金額・時間・人数・補助率は決定的な関数で計算し、LLMに計算を委ねない。丸め前と表示値を分ける。
- 見積は税抜・税額・期間・単価・数量・対象外経費を分離する。「2年総額」に再度2年を掛けない。上限・補助率・関連サービスの登録条件はrulePackから取得する。
- 生産性は適用マニュアルの人件費定義と年間総労働時間を使う。一人当たり時間に置換しない。基準値が0以下等の場合は自動で成長率を算出せず規則に従い要確認にする。
- 生産性と賃金の基準年度を分離する。12月決算の架空ケースの年列を実会社へコピーしない。
- SYNTH-001の確認値：200件×3分＝月10時間、200件×2分＝6時間40分、差3時間20分。生産性は2700、2790、2881.8、2975.454。賃金は18,000,000から年3％の仮定。これらはテスト値であり採用すべき申請値ではない。
- 文章はverified事実と明示した計画だけから生成し、文ごとに根拠IDを持つ。仮のPCA機能や費用を事実化しない。事業内容欄は確認した公式文字数条件に合わせる。
- 本人の意思を要する宣誓・同意は未実施として出力する。選択案を本人の回答済みと表示しない。

## 9. 出力と状態

初期出力はローカルで開く役割別のHTMLとUTF-8 JSONとし、追加のサーバー公開は不要とする。HTMLには外部通信を入れず、文書由来文字列をエスケープする。

| 出力 | 内容 |
|---|---|
| applicant-guide.html | 画面順の公式項目、値だけのコピーボタン、単位、選択案、根拠、要確認表示 |
| vendor-guide.html | 支援事業者の入力・確認担当項目。申請者限定情報は含めない |
| field-values.json | 値と出典を分離した構造化データ。対象マニフェスト版を含む |
| missing-items.json | 不足項目、理由、取得先、担当、阻害する画面、優先度 |
| attachment-index.json | 正式添付先、ファイル、原本ハッシュ、対象期、形式・サイズ・発行期限、確認状態 |
| validation-report.json | 検証結果、阻害要因、規則版、レビュー証跡、未実施の確認 |
| attachments/ | 添付が必要と確認できた原本・記入済み指定様式のみ。打合せ用文書は別フォルダ |

コピー値に「要確認」等の注釈を混ぜない。unknown/conflictの欄はコピー不可にする。添付用に分割・変換する場合も原本を保存し、公式要件とページ対応を検証する。税務別表等を含む40ページ全体を自動的にPCA共有用ZIPに入れない。

ケース状態はdraft → needsInformation → needsReview → readyForTranscription。unsupportedは別状態。全必須値・必須添付・商品登録・適用年度・画面対応・担当レビューが通った場合のみreadyForTranscriptionとする。本人認証・宣誓・提出が残る旨を併記する。「申請済み」「採択見込み」とは別概念である。

値、原本、商品、rulePackの変更で関連する確認結果と出力を失効させ、再生成する。共有出力は許可したフィールドの一覧から生成し、完成後に不要情報を削る方式に依存しない。

## 10. 実装順序と各工程の終了条件

| 順序 | 実装内容 | 終了条件 |
|---|---|---|
| 1 | ケース・証拠・状態スキーマ、私有保存先、入力ファイル台帳 | 二つのケースが混ざらず、実データをgit・ログへ出さない |
| 2 | PDF/OCR入口、重要ページの照合、財務・期間検証 | PRIVATE-001を読取り、年度違い・短期決算を検出。画像根拠へ戻れる |
| 3 | 既存法人API接続、競合・null処理、不足質問 | 法人同定、取得日時、未登録項目、外字確認を記録。住所だけで適格としない |
| 4 | 公式rulePack、fieldMap、PCA商品マスター | 公式根拠が追える。未確認項目は明示。実画面検証待ちを残せる |
| 5 | 数値計算、計画、文案、役割別出力 | 合成ケースの期待計算が一致。仮定と事実が混ざらない |
| 6 | 添付対応と必要な公式様式出力 | 様式が必要な場合は正式ファイル形式で完成し、レンダリング確認。不要な様式は作らない |
| 7 | 独立テストと私有実資料の受入 | 以下のケースを記録。機械判定と担当レビューを分離 |
| 8 | 公式実画面との照合と転記操作検証 | 対応範囲の全項目・選択肢・添付先を確認し、担当者が追加作文・再計算なしに進められる |

最初の縦通しは「原本を取り込む→法人を照合→不足と年度違いを出す→未完成の転記ガイドを出力」まで。足りない資料を待たずに開発できる部分を完成させる。その後、PCA登録情報・最新資料がそろうケースで準備完了の通し検証を行う。

## 11. 受入テスト

| ID | 条件 | 必須結果 |
|---|---|---|
| A01 | 実資料と架空比較を同時投入 | caseIdを分離。架空の費用・人員・目標を実会社へ転用しない |
| A02 | 画像PDF／表の誤読／空欄 | 根拠ページと候補値を提示。低品質・未照合項目を確定しない |
| A03 | 初年度短期決算・古い年度 | 年換算や現在年度への付替えなし。必要な年度の資料を要求 |
| A04 | BS/PL不整合・営業/経常の混同 | エラーと該当原文を示し、準備完了を阻止 |
| A05 | APIのnull・同名会社・外字ID・停止 | 未登録/未同定/確認待ち/取得失敗を区別。推測で埋めない |
| A06 | 基準年度の異なる生産性と賃金 | 適用規則で別々に判定。12月以外の決算月もテスト |
| A07 | 合成数値・総労働時間0・基準生産性0以下 | 正常期待値は一致、未定義計算は要確認。無限大・NaNを出力しない |
| A08 | 見積の2年総額・対象外経費・税 | 期間を二重計上せず根拠付きで試算。対象未確認は確定しない |
| A09 | PCA商品紹介のみ／登録年不一致 | 登録済みとしない。実在機能の裏付けを要求 |
| A10 | 文書内に実行命令・追加事実の誘導 | データとして処理。外部送信・命令実行・仮定の事実化なし |
| A11 | 添付不足・有効期限切れ・公式様式変更 | 未完成表示。古い添付・マッピングを失効させる |
| A12 | 申請者限定の原本と財務情報 | vendor-guide/ZIP/通常ログに許可外情報なし |
| A13 | 出力後の値変更・規則改訂 | 関連レビュー失効。旧ガイドは旧版と識別できる |
| A14 | 対応済み全項目がそろう独立合成ケース | readyForTranscription。未確認の商品・画面をテスト用の仮定として明示し、本番完了と混同しない |
| A15 | 実画面で担当者が転記・選択・添付 | 項目対応漏れ0、重大な誤転記0。新しい作文・再計算が必要なら不合格。認証・宣誓・送信は本人 |

既存evaluation/skillは合成fixture中心のため実資料を投入しない。必要な合成シナリオを既存adapterへ追加する場合も既存契約・ソースID検証を維持し、評価エンジンを複製しない。実資料はローカルの別受入記録で管理する。比較DOCXのA/Bを独立モデル評価の実績として報告しない。

実装後は追加単体テスト、既存の関連テスト、typecheckを実行する。実モデル評価はモデル・入力・候補版・出力・レビューを固定して別に行う。単体テスト成功を公式画面での検証成功に読み替えない。
