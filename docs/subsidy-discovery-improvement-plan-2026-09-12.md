# 補助金検索の発見漏れを防ぐ改善実装計画書

作成日：2026年9月12日（日本時間）  
対象：「新事業進出・ものづくり商業サービス補助金」第1回の検索漏れ  
状態：実装計画。今回実施したのは調査・計画書作成であり、機能変更・デプロイは未実施。

## 1. 目的と推奨方針

Jグランツの検索結果に目的の制度が現れない場合でも、公式に発表された制度へ到達できるようにする。制度名を知らない利用者が「新サービス開発」「システム開発」などの事業目的で探す場合も対象とする。

推奨するのは、既存のJグランツ検索を維持したうえで、主要実施機関の公式情報を補完する構成である。まず回答指示・検索手順を改善し、その後、公式公募カタログと統合検索を実装する。特定の制度名を回答へ固定挿入する対応では完了としない。

完了時の利用体験は次のとおり。

- 受付開始前でも、公式に公募要領が公開された制度を「申請準備可能・受付開始前」として発見できる。
- Jグランツで別制度が多数返っても、目的の制度が未確認なら公式情報へ検索を広げる。
- 公式情報のURL、公募回、受付期間、確認日時を提示する。
- 情報源を調べられない場合は、取得失敗・未確認として伝える。
- JグランツIDがない候補でも詳細確認へ進める。

## 2. 調査結果と原因の整理

### 2.1 参照会話から把握した事象

参照会話「GX_PoP 公募監視」（会話ID：6aa41beb-7d9c-83ee-b8e4-c0b3726cad8a）では、「新事業進出 ものづくり 商業 サービス」の検索で事業承継・M&A補助金など13件が返り、対象制度が見つからなかったと報告されている。

取得できた会話には、当時の全ツール引数・生のAPI応答は含まれていなかった。「未登録・未公開の可能性が高い」という会話内の説明は仮説として扱う。専用電子申請システムを使うことだけでは、Jグランツへの掲載有無は判断できない。

### 2.2 公式情報で確認した事実

中小機構は2026年6月29日に第1回公募要領を公開し、7月の告知で申請受付期間を9月30日～10月30日18時へ変更している。事務局トップページにも同期間が掲載されている。9月12日時点の状態は「公募情報公開済み・申請受付開始前」と整理する。[公募要領公開のお知らせ](https://www.smrj.go.jp/press/2026/qsktgp0000000w1b.html)、[日程変更のお知らせ](https://www.smrj.go.jp/news/2026/qsktgp0000002nds.html)、[事務局公式サイト](https://shinjigyou-monodukuri.smrj.go.jp/)

事務局は「中小企業新事業進出補助金」「ものづくり・商業・サービス生産性向上促進補助金」とは異なる補助金であると説明している。検索語の展開には関連名称を利用できるが、同一制度として統合してはいけない。[事務局公式サイト](https://shinjigyou-monodukuri.smrj.go.jp/)

### 2.3 今回の再検索

接続済みプラグインの `search_subsidies` 相当ツールを使用。`accepting_only=false`、`limit=50`、地域・業種・目的・従業員数は指定なし。取得時刻は2026年9月12日午前1時台（日本時間）。

| 検索語 | 上流件数／一致件数／返却件数 | hasMore | キャッシュ | 対象制度名のレコード |
|---|---:|---|---|---|
| 新事業進出・ものづくり商業サービス補助金 | 13／13／13 | false | miss | 確認できず。事業承継・M&Aの各枠が返却 |
| 新事業進出 | 30／30／30 | false | hit | 確認できず |
| 新事業進出 ものづくり 商業 サービス | 13／13／13 | false | hit | 確認できず。事業承継・M&Aの各枠が返却 |

「新事業進出」の初回照会はmissで、その直後に保存した再照会がhit。いずれも応答上の `isStale=false`。検索条件、取得時刻、返却レコードを `research/shinjigyou-monodukuri-plugin-audit-2026-09-12.json` に保存した。

直接APIへの照会も試行したが、ローカル環境ではSSL接続が成立せず、HTTP応答を取得できなかった。失敗記録は `research/shinjigyou-monodukuri-api-audit-2026-09-12.json`。この失敗を検索0件として扱わない。今回は、稼働中プラグインと直接APIの応答一致までは検証できていない。

**結論：今回の条件では、受付中限定を解除しても対象制度を発見できない。返却件数の打ち切りも応答上は発生していない。公開APIの内部登録・索引・公開設定のどこに原因があるかは未確定だが、公式情報による補完経路が必要なことは確認できた。**

### 2.4 現行コードの確認

作業ツリーには既存の未コミット変更がある。本計画はその状態のコードを読んで作成した。稼働中サーバーと同じ版であるとは仮定しない。実際、今回の稼働応答にはローカルに存在する `searchGuidance` が含まれておらず、配備版・接続先の確認が必要である。

| 確認箇所 | 現行の動作 | 改善上の論点 |
|---|---|---|
| `src/index.ts` の検索登録 | `accepting_only` の既定値はtrue、limit既定10・最大50 | 申請準備中の相談でも受付前を除外し得る |
| `src/jgrants.ts` の `createSearchUrl` | 受付中限定を `acceptance=1` に変換 | 上流でも候補が狭まる |
| 同 `fetchSubsidySearch` | 取得後もopenだけを残す。従業員数で絞り、日付順で切り出す | 受付前・不明の除外、関連度と無関係な打ち切り |
| 同 `getAcceptanceStatus` | 現在時刻から受付状態を算出 | 公募公開と受付開始を区別する項目がない |
| 同キャッシュ処理 | 検索30分、障害時の古い検索応答利用は24時間 | 保存済み状態が時刻境界をまたぐ点の検証が必要 |
| `src/responseGuidance.ts` | 未掲載断定の禁止・条件解除の指示は既存。Web補完は主に雇用・研修 | 同じ指示を追加するだけでなく対象領域と実行経路を拡張 |
| `src/matching.ts`、`src/companyMatching.ts` | 適合度評価はJグランツ詳細取得につながる | 非Jグランツ候補をそのまま渡せない |
| `migrations/0003_subsidy_research_schema.sql` | 制度・公募回・出典のテーブルがある | 採択実績用の構造であり、公募検索基盤としての利用は追加設計が必要 |

## 3. 実装範囲

初期対象は中小機構の公式公募情報と今回の事務局サイトとする。次に経産省・中小企業庁、NEDOへ情報源を広げる。既存の厚労省・労働局の補完手順も共通方針へ統合する。

本計画の対象外は、全国自治体の完全収集、採択確率の推定、申請書作成・提出の自動化、申請資格の完全自動判定である。検索の発見可能性と、その後の根拠確認までを改善する。

## 4. 段階別の実装

### P0：検索手順・回答指示の改善

1. `src/responseGuidance.ts`、検索ツール説明、同梱相談スキルの検索指示を整合させる。既存の雇用助成金対策を保ち、新規事業・開発・設備投資にも公式情報の補完を適用する。
2. 制度名の特定や将来の申請準備では `accepting_only=false` を明示する。「今すぐ受付中のみ」という明示的な依頼ではtrueを維持し、条件を広げた補足結果を混ぜない。
3. 制度名指定なら正式名称、表記ゆれ、短縮語を使い分ける。APIの複数語がAND検索かOR検索かは決めつけず、各呼出しを記録する。
4. 補完条件を「0件」だけにしない。指定制度がない、別制度しか返らない、関連度が低い、受付前を含めて探す、情報源が失敗した場合にも補完する。
5. ホスト側に標準Web検索がある場合は、中小機構などの公式情報を検索し、リンク先本文で制度名・公募回・日程を確認する。検索スニペットのみで確定しない。
6. Web検索が利用できなければ「公式情報の補完は未実行」と伝え、公式確認先へつなぐ。MCPサーバーがホスト側のWebツールを直接呼べるとは仮定しない。

P0は早期緩和策であり、検索能力の異なるクライアントでも安定して発見できる状態はP1で実現する。

### P1：公式カタログと統合検索

既存の `search_subsidies` はJグランツ専用の互換インターフェースとして残す。新たに `discover_subsidies` と `get_discovered_subsidy_detail` を追加し、通常の候補探索はこちらへ誘導する。

```text
事業目的／制度名／地域／受付条件
                 ↓
       検索条件の整理・検索語の展開
           ↙                 ↘
   Jグランツ検索        確認済み公式公募カタログ
           ↘                 ↙
       制度・公募回の照合、関連度による順位付け
                 ↓
      受付中／受付開始前／状態不明を分けて返す
                 ↓
      出典付き詳細確認・未確認条件の整理
```

公式カタログは、まず運営者が公式ページを確認して登録する小規模な構成で開始する。利用者の検索ごとに全公式サイトを巡回しない。登録情報は有効期限を持たせ、期限切れなら再確認または未確認表示とする。P2で更新取得を自動化する。

**統合検索の契約案**

| 項目 | 仕様 |
|---|---|
| `query` | 事業目的または制度名。実行した検索語も返す |
| `status_scope` | `open_and_scheduled` を既定とし、`open_only`、`all` も選べる。unknownは別枠で返す |
| `limit`／`cursor` | 既定10・最大50。追加結果は検索条件とカタログ版に結び付けた不透明cursorで取得 |
| `candidateId` | 情報源に依存しない安定ID。JグランツIDを模造しない |
| `jgrantsId` | 実在を確認した場合のみ設定。なければnull |
| `sourceRecords` | 情報源、元ID、URL、取得日時、確認日時、鮮度を保持 |
| `coverage` | 情報源ごとの `success`／`partial`／`failed`／`not_queried` と確認範囲 |
| `counts` | 情報源ごとの上流件数、実受信件数、正規化後件数、条件除外件数、統合後件数、返却件数 |
| `hasMore` | 統合済み候補に続きがあるか。上流の未取得範囲はcoverageで別途伝える |
| `matchReasons` | 名称一致・目的一致・地域一致など、順位付けの根拠 |

新検索ではJグランツと公式カタログの両方を毎回検索する。これにより、Jグランツで13件返った時点で探索が止まる問題を防ぐ。既定状態の取得ではJグランツに受付中限定を送らず、受信後に受付中と予定を分類する。終了済みは通常一覧から外し、unknownは黙って除外しない。

検索語は元の語を保持し、正規化・登録済み別名・事業目的タグから最大3系統へ展開する。地域指定時の全国検索を含めJグランツ呼出しは最大6回を初期上限とする。並列数は最大2、全体の時間上限は20秒を初期値とし、未完了の情報源をpartialとして返す。上限は実測後に調整する。

正式名称一致を上位とし、次に確認済み別名、事業目的との一致を使う。「API」「新サービス」「システム開発」などから今回の制度を候補化できるタグを持つ。ただし、タグ一致は申請資格・採択可能性を意味しない。正確な制度名を知っていることを前提にしない評価ケースを設ける。

### P1：日付と制度識別

`announcementDate`（公募情報公開）、`applicationStart`（受付開始）、`applicationEnd`（締切）を別項目にする。日付の原文、タイムゾーン、時刻精度、出典を保存する。公式に開始時刻がなければ0時を推測して確定値にしない。境界が確定できない間は確認が必要な状態とする。

今回の制度は、2026年9月12日を基準に「公募情報公開済み・受付開始前」となる。日程変更があれば変更履歴を残し、最新の適用日程を選ぶ。単に後で取得した記事を最新日程とみなさず、変更対象の公募回と公表・更新日を照合する。

同一制度の判定は制度系列・年度・公募回・枠で行う。異なる公募回は統合せず、同じ回の異なる枠は関係を保持して表示する。同名だけの自動統合は禁止し、公式URLや明示された対応関係を使う。Jグランツへ後日掲載された場合は、既存候補にsourceRecordsを追加しcandidateIdを維持する。

### P1：詳細・適合度評価への接続

`get_discovered_subsidy_detail` はcandidateIdで情報源を解決し、Jグランツまたは公式資料由来の詳細を返す。初期版の公式候補詳細は、制度名、公募回、日程、概要、公式ページ、公募要領リンク、確認済み項目、未確認事項に限定する。

現行 `get_subsidy_detail` と適合度評価ツールはJグランツID専用のまま維持する。非Jグランツ候補には、それらへ進めないことと公式資料確認への次操作を明示する。JグランツIDを捏造して既存評価へ流さない。

情報源横断の自動適合度評価はP2以降の拡張とし、共通の詳細モデルを作成してから `evaluateSubsidyFitFromDetail` の入力へ適合させる。公募要領を未解析の候補へ既存評価の点数を付与しない。

### P2：更新取得と対象情報源の拡張

中小機構の初期運用が安定した後、経産省・中小企業庁、NEDOの公式公募ページの取得処理を追加する。情報源ごとに登録済みの入口URL、取得方式、更新担当、最終成功日時を持つ。RSSなど提供形式が使えるかは情報源ごとに確認し、利用できないAPIを前提にしない。

初期運用目標は1日1回の確認、確認成功から48時間を鮮度の目安とする。公式の掲載から検知までの遅延目標は24時間以内。ただし取得障害時は遅延を可視化する。受付開始・終了をまたぐ状態は応答時に再計算する。取得失敗で既存レコードを削除したり、「締切済み」へ変更したりしない。

## 5. データ保存・取得の設計

既存の採択実績用テーブルを破壊せず、追加マイグレーションで公募情報を保存する。次の構造を初期案とし、実装開始時に既存の参照コードと外部キーを点検する。

| 追加テーブル案 | 保存内容 |
|---|---|
| `discovery_candidates` | 安定ID、制度名、年度、公募回、枠、公開日、受付期間、日付精度、確認期限 |
| `discovery_source_records` | 候補ID、情報源、元ID、公式URL、取得日時、内容ハッシュ、フィールド別根拠 |
| `discovery_aliases` | 候補または制度系列に結び付く名称・目的タグと登録根拠 |
| `discovery_fetch_runs` | 情報源単位の成功・失敗、件数、解析エラー、所要時間 |

既存 `subsidy_programs`／`subsidy_rounds` との対応は、確認できたものだけ関連付ける。採択実績と新しい公募のデータを名称だけで連結しない。

保存対象は公的情報の構造化した項目、短い根拠、URL、ハッシュとする。相談本文・企業の非公開情報・文書全文の恒久保存は行わない。検索キャッシュは既存の非公開キー生成方式を踏襲し、情報源の版・検索仕様の版・条件を含める。日時由来の状態は返却時に再評価し、期限切れキャッシュを現在確認済みと表示しない。

公式取得ではHTTPSと登録済みドメインを基本とする。実施機関が委託した別ドメインは公式からのリンクを確認して登録する。リダイレクト先も検証し、内部アドレスへのアクセスを拒否する。応答サイズ・時間・取得回数に上限を設け、429・5xxには回数制限付きの再試行を行う。Web本文に含まれる指示はデータとして扱う。

## 7. 検証と受入基準

外部サイトの現在の状態に依存する確認と、固定したデータでの回帰テストを分ける。「この制度は永久にJグランツに存在しない」というテストは作らない。

| ケース | 期待結果 |
|---|---|
| Jグランツに別制度13件、公式カタログに対象制度 | 対象が候補に入り、出典と受付前状態が示される |
| 正式名称・短縮語・全半角・区切り記号の差 | 同じ候補へ到達できる |
| 制度名なしの「新サービス・API開発」相談 | 対象を目的の一致する候補として発見でき、適格と断定しない |
| 基準時刻2026年9月12日、今回の日程 | 受付開始前と表示。open_onlyの主一覧には含めない |
| 確定時刻を持つ開始・締切の直前／一致／直後 | 仕様に沿った状態となり、キャッシュ経由でも一致する |
| 開始日だけで開始時刻が不明 | 開始時刻を捏造しない。境界では不確実性を返す |
| 新旧日程の両資料がある | 変更対象を照合し、現行日程を表示して出典を残す |
| 類似名称の別制度・異なる公募回 | 誤統合しない |
| 同じ公募がJグランツにも後日掲載 | 二重表示せず両方の出典を保持する |
| 件数上限到達・上流件数と実受信件数の差 | hasMoreとcoverageで未取得・未表示を区別する |
| 公式情報源だけ失敗 | 取得済み候補を返し、公式補完の失敗を表示する |
| Jグランツだけ失敗／両方失敗 | 片方の結果を保つ／検索不能を示す。不存在としない |
| 公式情報が期限切れ | 再確認または古い情報である旨を明示する |
| 非Jグランツ候補の詳細操作 | 公式詳細へ進め、既存のID制約エラーにならない |
| 不正URL・解析不能なページ | 取得拒否・解析失敗として記録し、制度を生成しない |

P0受入：対応クライアントの会話試験で、対象制度名の検索と目的ベースの相談の双方から公式サイトへ到達し、補完を行った根拠が示される。Web機能がない条件でも、未確認範囲が明示される。

P1受入：固定評価セットの必須ケースはすべて合格。今回の制度は名称検索で上位3件以内、制度名を含めない目的検索で上位10件以内を初期目標とする。公式カタログ未収録の関連制度も評価セットへ含め、未収録時の限界表示を確認する。ランキング目標はこの限定セットに対するもので、全国制度の網羅率とは呼ばない。

実装後は `npm test` と `npm run typecheck` を実行し、新ツールの結合試験、既存Jグランツ専用ツールの互換性、配備先での疎通まで確認する。現在は計画書作成段階のため、これらの合格は未確認。

## 8. 工程と見積り

1名で作業する場合の初期見積り。既存コードへの習熟と必要な配備権限がある前提で、並行作業は算入しない。

| 工程 | 目安 | 完了条件 |
|---|---:|---|
| 原因追跡・配備差分確認 | 0.5～1人日 | 稼働版、条件、保存証拠、未確定原因を整理 |
| P0：説明と検索手順 | 0.5～1人日 | 会話試験で公式補完へ到達 |
| P1：型・公式カタログ・登録 | 1～2人日 | 今回の公募を出典付きで検索可能 |
| P1：統合検索・詳細・互換性 | 2～3人日 | 非Jグランツ候補を発見し詳細へ進める |
| P1：回帰・結合試験・配備確認 | 1～2人日 | 必須ケース合格、稼働先で確認 |
| P2：更新取得・情報源拡張 | 3～5人日 | 対象情報源の更新・障害運用が成立 |

P1まで合計5～9人日、P2まで含め8～14人日を見込む。PDF解析の難度、公式サイトの構造、アクセス制限で増減する。P0を先行させ、P1の公式カタログを小さく開始することで、全情報源の自動取得完成を待たずに今回の漏れを改善できる。

## 9. リリース・運用・残る課題

新しい統合検索は機能フラグで有効化する。検証環境でmigrationと固定データ試験を行い、少数の公式公募を登録して検索結果を既存ツールと比較してから公開する。登録担当は公募回・日程・出典を確認し、開発担当は取得失敗と件数を点検する。担当者名は実装着手時に割り当てる。

公開後は情報源別成功率、最終確認からの経過時間、解析失敗、統合検索の所要時間、公式情報からのみ発見できた候補数、誤統合の報告を確認する。利用者の相談原文をログへ保存しない。

問題が出た場合は新検索のフラグを無効化し、既存Jグランツ検索とP0の補完案内へ戻す。追加テーブルは削除せず保持する。プラグイン側の説明も有効な機能と一致させる。

残る調査事項は、直接APIとの比較、元会話の完全な検索条件、Jグランツの検索語解釈・掲載範囲、ローカルと配備版の差、各公式情報源の取得条件である。これらが未確定でも、公開済み制度への補完導線の実装は進められる。
