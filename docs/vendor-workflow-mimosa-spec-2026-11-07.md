# 販売会社別の申請支援手順 — ミモザ情報システムを想定した仕様

作成日：2026年11月7日（日本時間）

版：0.1／次版向け仕様案

状態：仕様化済み。実装・実モデル評価・配布版更新・OpenAIへの更新申請は未実施。

想定利用者：販売会社を通じてPCAクラウド会計を導入する申請者。販売会社の担当者による利用も可能。

位置づけ：既存の[PCA申請準備仕様](pca-it-grant-application-assist-spec-2026-11-05.md)を補足する。申請者中心の対話と販売会社別手順について本書を採用し、既存の根拠・計算・共有・転記完了の検証条件は維持する。

## 1. 目的と今回の決定

**購入予定の製品・販売会社を起点に、申請者が「資料をそろえる・内容を確認する・所定の画面に入力する」ことで申請準備を進められるようにする。販売会社ごとの依頼書、受け渡し順、受付期限を、共通の申請支援手順に組み合わせる。**

ミモザ情報システムを最初の参照事例とする。公開情報に基づく手順案であり、同社との提携、監修、導入合意、個別案件の受付承諾を示すものではない。利用者が別の販売会社を選んだ場合に、ミモザへ誘導しない。

次版の中心はスキルと参照資料の改善とする。専用管理画面、販売会社のAPI、新規の公開MCPツールがなくても、会話・既存の公開情報照会・ホストのWeb閲覧とファイル読取りで役立つ範囲を提供する。

### 1.1 改善する動作

- 見積や商品URLから分かる内容を先に読み、不足だけ質問する。
- 販売会社の既存書式・手順を使い、独立した提案書の新規作成を一律に要求しない。
- 導入目的の聞き取りを、申請項目と製品の適合確認に必要な範囲に収める。現状と目標が分かれば説明案を作り、確認後は書類準備へ進む。
- 製品機能や登録情報の回答待ちでも、依存しない書類整理を進める。
- 国の要件、販売会社の運用、プラグインの実装範囲を明確に区別する。
- 申請者自身の確認、同意、認証、提出が必要な場面を、具体的な操作として案内する。

### 1.2 次版の範囲

| 区分 | 次版で扱う内容 | 到達点 |
|---|---|---|
| 共通 | 会社・製品・購入先・年度の把握、資料整理、導入目的の説明案、不足情報の確認依頼 | 申請準備を継続できる |
| ミモザ向け | 公開手順を使った見積依頼、同社書式の受領と確認、担当工程への案内 | 販売会社への確認・受け渡し準備 |
| 制度・製品照合 | 通常枠とインボイス枠（インボイス対応類型）の候補説明、該当年度の根拠取得 | 確認済み／未確認／実装範囲外を区別 |
| 厳密な転記ガイド | 既存実装が扱う2026年第7次以降・通常枠・標準補助率・申請額5万円以上150万円未満・過去受給なしの範囲 | 既存検証を通過した案件のみ転記準備完了 |
| 2027年度等 | 公表状況を確認し、年度非依存の事前整理を継続 | 年度・公募条件の確認待ち。正式な申請ガイド完成とはしない |

ミモザが案内する申請枠と、プラグインが正式転記まで対応する枠は一致するとは限らない。実装都合で通常枠へ変更したり、未対応の枠を制度上の対象外としたりしない。対象拡大は、その枠の制度・計算・様式・画面の受入を別に満たして行う。

## 3. 共通手順と販売会社別手順の構造

| 情報の層 | 管理する内容 | 主な根拠・変更条件 |
|---|---|---|
| 制度 | 年度・公募回・枠・申請資格・計算・添付・公式画面 | 適用する公式要領・改訂通知・マニュアル・実画面 |
| 製品・登録 | プラン、機能、利用単位、登録ITツールと支援事業者の組合せ | メーカー資料、当年度の登録資料、該当案件の見積 |
| 販売会社の手順 | 見積窓口、所定書式、受付期限、受け渡し順、担当窓口 | 販売会社の公開案内、実際の書式、案件への回答 |
| 案件 | 会社、利用者の目標、受領書類、確認済みの値、待ち作業 | 本人の回答、原本、照会結果。非公開で管理 |

国の条件は制度の層で判断する。販売会社の書式や内部期限は、その販売会社を選んだ案件にのみ適用する。製品紹介だけで補助金の登録を確定しない。

公式概要ページと対象公募の詳細マニュアルで入力担当等が異なる場合は、適用版・該当画面を確認する。根拠の不一致を隠して一方を採用せず、影響する工程を確認待ちにする。

### 3.1 販売会社プロファイル

共通の進め方をスキル本文に置き、販売会社ごとの情報を参照資料に分離する。次版では1社でも、同じ項目で2社目を追加できるようにする。

| 項目 | 内容 |
|---|---|
| `vendorKey` / `profileVersion` | 内部識別子と版。例：`mimosa-pca` / `0.1-draft`。公的登録番号ではない |
| `displayName` / `identitySource` | 販売会社名、運営者を確認した出典 |
| `applicability` | 公開案内が対象とする年度・枠・製品群。`unknown`を許容し、全年度有効にしない |
| `sources` | URL、発行主体、取得日時、ページ記載の更新日、該当見出し、取得・確認状態 |
| `channels` | 見積依頼・問い合わせ・申込書返送の窓口。リンク確認と実操作確認を分ける |
| `workflowSteps` | 各工程の担当、前提、必要入力、出力、完了証拠、影響する後続工程 |
| `forms` | 書式名、発行元、対象年度、版、原本、入力欄の対応、同意・署名欄、宛先 |
| `deadlines` | 事務局期限と販売会社期限を別項目で保持。未公表の日付は`null` |
| `registrationEvidence` | 当年度の登録根拠。販売会社の案内だけなら確認待ち |
| `supportBoundaries` | 公開されている支援範囲、案件ごとの追加条件、未確認事項 |

各事実には `sourceId`、`status`（確認待ち／取得済み／内容確認済み／競合／期限切れ）、`checkedAt`、`applicableYear` を付ける。「サイトに書かれていることを確認済み」と「当該案件で受付・登録を確認済み」は別の事実として保持する。プロファイル全体に単一の「確認済み」を付けて欠落を覆わない。

### 3.3 あらかじめ整備する情報と、案件ごとに確認する情報

販売会社ごとの公開手順・有効な共通書式・製品情報は、一度内容を確認した版を再利用する。案件ごとに同じ資料を販売会社へ請求し直す運用を標準にしない。

登録情報は「制度年度 × 申請枠 × 登録主体・構成員 × ITツール番号 × 正式プラン・登録版」の組合せで照合する。同名製品でも別の販売会社の登録を流用しない。既知の組合せに一致し、根拠の有効性が確認できれば、販売会社への再問い合わせを省略できる。

案件ごとに確認するのは、見積価格・人数・期間・追加役務・個別期限・受付承諾・本人の事実と計画等。個別の回答や非公開書式を他社案件向けの共通知識に昇格するには、共有可能な範囲と適用条件を別に確認する。

## 4. 利用者に見せる4段階

既存の4段階を維持し、販売会社の手順を内部に組み込む。初回に役割分担や内部データ構造を説明しない。

| ステップ | 利用者の操作 | プラグインが行うこと |
|---|---|---|
| 1. 会社・製品・購入先を確認 | 会社を選ぶ。見積・商品URL・購入先があれば示す | 公開情報と見積を読み、年度・候補枠・購入先・製品を整理 |
| 2. 書類をそろえる | 手元の書類を添付し、不足書類を取り寄せる | 公式提出用、販売会社用、計算・確認用を区別した一覧を提示 |
| 3. 内容を確認する | 値・説明案・本人が決める計画を確認する | 整合性検証、対象範囲内の計算、説明案、販売会社への不足確認を用意 |
| 4. 申請画面へ進む | 販売会社の案内と公式画面に沿って入力・添付・最終確認 | 対応済みの画面順に案内。本人認証・同意・宣誓・提出を本人へ引き継ぐ |

4段階は案内上の区分であり、4操作での完成や進捗率を意味しない。販売会社への申込は必要な準備が整った時点で行え、ステップ3の全作業が終わるまで一律に待たせない。

### 4.1 入口の処理順

1. 会話・受領資料から既知の会社、製品、販売会社、年度、希望枠を引き継ぐ。年度・枠を既存実装の初期値で補わない。
2. 会社が未確定なら既存の会社選択手順を使う。会社・資料の不一致は、対象範囲を絞って確認する。
3. 見積書があれば発行者・宛名・製品・期間・人数・費用をまとめて読み取る。購入先は発行者を候補として示す。利用者が既に明示していれば聞き直さない。
4. 購入先が未定なら「決まっている／相談中／未定」で次の案内を分ける。本書の参照例や閲覧したURLだけでは、案件の購入先を確定しない。
5. 申請年度を確認し、制度と販売会社手順の適用可否を判定する。未確認年度でも独立した準備へ進む。
6. 製品・登録情報から候補枠を整理し、本人の意向と条件を照合する。単に補助率が高いという理由だけで枠を確定しない。
7. 対象年度の要件が確認できる場合は、業種・規模・資本関係・過去受給・契約状況等の入口条件を早めに照合する。公開情報や受領資料で補い、不足だけ本人に確認する。上場予定だけで対象可否を決めず、APIで補助金履歴を取得していないことを過去受給なしと扱わない。

### 4.2 導入目的の聞き取り

標準入力は「現在の業務・困りごと」「導入後に実現したいこと」。既に分かれば質問は不要。用途不明の追加質問を続けず、説明案を先に提示する。

追加質問は、(a) 必須申請項目の欠落、(b) 根拠との矛盾、(c) 製品の適合に影響する不明点、(d) 本人だけが決められる計画、のいずれかに対応させる。金額、時間削減率、人数、上場時期、審査上の効果を創作しない。計画数値に必要な根拠は、その段階で確認する。

例：現在のソフト、メール等による承認、権限管理を整備したい目標が既知なら、現状と目標を説明案にまとめる。実現できる製品機能は別途確認し、未確認の機能や効果は確定した申請文に入れない。既存ソフトにその機能がないとも断定しない。

### 4.3 販売会社への問い合わせ

先に公開情報・メーカー資料・受領書類を確認する。未確認の項目は重複を除き、原則一つの確認依頼にまとめる。既に有効な回答がある項目を再質問しない。

問い合わせの候補は、正式プラン、追加製品の要否、登録番号・対象年度、見積内訳、移行範囲、所定書式、受付期限。案件で必要な項目だけ採用する。提案書の形式を必須にせず、既存資料、見積の追記、担当者の回答でも受け付ける。口頭回答は利用者の申告として保持し、登録等の証拠が必要な事項は根拠確認を残す。

依頼文の作成・利用者による送信・相手の受領・回答取得を別々に記録する。文面を作っただけで送信済みにしない。ホストで外部送信できる場合も、その時点の利用者の明示的な送信依頼と共有範囲に従う。

## 5. ミモザを選んだ案件の進め方

以下はM01を参照した製品側の工程設計。実際の書式や個別案内を受け取ったら、適用条件を照合する。

| 工程 | 利用者へ案内する次の操作 | 完了の扱い |
|---|---|---|
| W01 購入先の指定 | ミモザで相談・購入する旨を指定 | 明示指定、または見積から示した候補への本人確認 |
| W02 見積準備 | 補助金利用希望を添え、製品・人数・期間を確認して見積を依頼 | 依頼文作成／送付／見積受領を区別 |
| W03 見積・商品照合 | 読み取った製品・金額・期間を確認 | 原本照合と本人確認。登録・機能の未確認は別途保持 |
| W04 所定書式 | 同社から実際の申込・同意書を受け取り、必要箇所を確認・記入 | 原本・版・対象案件を確認。同意・署名は本人 |
| W05 同社への申込 | 指定の宛先・方法・期限に沿って書式を送る | 準備済み／本人申告の送付済み／受付確認を区別 |
| W06 公式申請の開始 | 実際に届いた案内から申請マイページを開く | 招待の受領等を確認。URL・期限を作らない |
| W07 申請者・支援事業者の入力 | 当該画面の担当に沿って転記・添付し、必要な情報を受け渡す | 最新の公式画面対応と本人・担当者確認に基づく |
| W08 最終確認・提出 | 本人が内容・宣誓を確認し、公式画面で提出 | 準備完了と提出済みを区別。提出結果が未取得なら未確認 |

見積受領や申込・同意書への記入を、製品の発注・契約と自動的に同一視しない。実際の書式に購入契約等の条項があれば、その該当箇所を提示して確認する。通常の通販注文へ自動で進めず、対象制度の交付決定と発注条件に沿って案内する。

交付後は購入・導入・実績報告等の後続手続きがあると案内するが、次版の正式な出力・操作受入範囲は交付申請準備までとする。販売会社の案内を示しただけで後続手続き全体を実装済みとしない。

## 6. 「確認待ち」でも進めるための状態管理

### 6.1 案件全体を一つの待ち状態にしない

| 待っている情報 | 進められる作業 | その情報が必要な作業 |
|---|---|---|
| 製品の承認・権限機能への回答 | 会社情報、手元資料の整理、現状・目標の下書き | 機能を断定する説明、構成確定 |
| ITツール・支援事業者の登録根拠 | 見積読取り、本人の課題整理 | 補助対象確定、登録に依存する申請額、公式転記完了 |
| 販売会社の所定書式 | その他の必要書類の整理 | 書式記入・同意・返送 |
| 販売会社の受付期限 | 既知の準備 | その会社で締切に間に合うという確約 |
| 2027年度の公式要件 | 現在の会社情報、希望製品、手元の見積、現状・目標の整理 | 対象年度の資格・補助額・必要決算期・最終添付・正式画面の確定 |

### 6.2 進捗と確定値の区別

販売会社工程の状態は `notStarted / preparing / waitingApplicant / waitingVendor / readyForUserAction / completed / notApplicable` とし、画面では自然な日本語で表示する。各状態に理由・根拠・更新日を付ける。`completed`は該当工程だけの完了であり、申請全体の完成ではない。

既存エンジンの `unsupported / needsInformation / needsReview / readyForTranscription` は制度・証拠・転記の判定として維持する。年度未対応は失格ではなく実装範囲の表示とする。販売会社プロファイルを読んだだけでは、`readyForTranscription`へ昇格しない。

利用者へは「見積の読取り済み／登録情報は回答待ち／次は手元の決算資料を確認」のように、完了した作業と次の操作を示す。必須項目が未確認のまま、公式提出可能と案内しない。

## 7. 資料・根拠・共有

### 7.1 資料一覧

一つの一覧に、資料の正式名称、必要年度・期間、取得先、使う場所、現在の状態、次の操作を載せる。用途を次の三つに区別する。

1. 公式提出用：対象年度・枠の要領とマニュアルで必要性を確認した書類。
2. 販売会社用：同社が発行する申込書・同意書、案件別に指定された資料。
3. 内容確認用：見積内訳、製品機能資料、計算の根拠資料等。

条件付き書類は条件を表示する。年度未確定時は「手元資料の整理」とし、公式の必要書類一覧が確定したように見せない。公的証明書の発行期限が不明な段階で一律の取得を促さない。販売会社の概略一覧だけで、すべての資料に同一の有効期限を適用しない。

### 7.2 読取りと確認

既存の原本ハッシュ・物理ページ・項目ラベル・単位・期間・確認状態を保持する。名称・宛名を修正した架空見積は、実見積へ昇格しない。実会社と架空例は別の案件・根拠IDで扱い、公開の仕様・評価データへ実会社の申請情報を転記しない。

価格は「公開参考価格」「案件の見積価格」「補助対象経費」を別値にする。利用期間総額を月額として再乗算しない。税・追加役務・割引・対象期間は既存の数値検証へ渡す。制度未確認年度では見積の合計確認はできるが、補助金額の確定には進めない。

### 7.3 出力と共有範囲

| 出力 | 内容と宛先 |
|---|---|
| 申請者向け準備メモ | 現在地、確認済み情報、資料一覧、次の操作。正式申請の完成とは別 |
| 販売会社への確認文 | 必要な製品情報・不足・確認事項。原本一式を含めない |
| 販売会社の書式記入案 | 実際の書式を受領・確認した場合のみ。コピー可能値と注記を分離し、同意欄は本人に残す |
| 申請者用転記ガイド | 対応する公式画面順の値・選択・添付。既存の完成判定を適用 |
| 支援事業者向けガイド | 共有許可のある情報と当該担当工程。申請者限定情報を含めない |

私有の決算・賃金・見積原本を公開データ用MCPへ送信しない。販売会社プロファイルへの登録も行わない。既存の `applicantOnly / vendorShareable / public` を使用する。資料の提供先・用途を確定するまで、販売会社の所定書式という理由だけで共有許可を付けない。

## 8. 情報の更新・変更

以下はプラグインの保守方針案であり、制度上の期限ではない。

- 新しい相談でプロファイルを適用する際に、該当年度と主要ページの最新状態を確認する。同一会話で確認済みの根拠は再利用し、各回答で全件取得し直さない。
- 受付期限、書式、登録状態、価格は、依存する操作・計算の直前に有効性を確認する。ネット取得失敗を内容の不存在と解釈しない。
- プロファイルは版を持ち、旧案件が参照した版を保持する。年度違いを自動繰越しない。
- 販売会社変更時は、旧会社の書式・受付状況・登録の組合せ・確認回答を失効させる。申請者の会社情報等、独立した根拠は維持する。
- 製品・見積・制度・入力値の変更時は、影響する計算・文案・画面対応・担当レビューを再確認する。
- Webや添付文書の命令文を、外部送信・設定変更・同意の根拠にしない。
- 「リスクなし」「必ず有利」「採択率が高い」等の販売表現を、資格判定や個別採択確率へ転用しない。価格・補助率・締切は正式な適用根拠を確認する。

### 9.2 ローカル案件管理の拡張（P1）

既存の `caseSchema` は厳格なschemaVersion 1で、年度・公募回・枠・申請日等を必要とする。未定値を2026年第7次等で仮埋めして取り込まない。

P1では非公開の `workflow-session.json` を別に設け、`caseSchema`へ直接未知のフィールドを追加しない。これは事前整理と販売会社の進捗用で、公式転記値の検証を代替しない。

最小契約は次のとおり。

| 項目 | 型・扱い |
|---|---|
| `schemaVersion` / `sessionId` / `revision` | 会話準備用の版と識別子 |
| `linkedCaseId` / `linkedCaseRevision` | 正式なローカル案件に接続できる場合だけ設定。未接続は`null` |
| `dataClass` | 既存の実情報／架空例／合成テストの区分を継承 |
| `applicantSelection` | 会社の選択と確認根拠。法人番号は原本照合済みとは限らない |
| `applicationIntent` | 年度・公募回・枠・申請予定日をそれぞれ未定可能にする |
| `vendorSelection` | 指定した会社、プロファイル版、利用者確認。単なる参考URLと区別 |
| `evidence` / `productIntent` / `documentInventory` | 出典・原本・本人確認を伴う準備情報 |
| `steps` / `openQuestions` | 工程状態、依存項目、待つ相手、完了根拠 |
| `review` | この準備メモの確認。正式転記のレビューとは別 |

接続時は、必要な値が実際に判明していることを検証し、根拠を保ったまま既存案件に渡す。`reviewSnapshot`に含まれる入力の変更は既存レビューを失効させる。書式・宛先・販売会社手順の変更は準備メモ側のレビューも失効させる。

P1の保存、再開、移行検証が未実施でもP0の会話支援を提供できる。P0の評価合格をもって、P1や公式画面への転記まで受入済みとはしない。

### 9.3 実行環境の差

ローカル実行・ファイル出力が使える環境では既存入口を利用する。利用できないホストでは会話内の整理・文案・確認事項までとし、ローカル検証・保存・正式ガイド出力を実行済みと説明しない。質問UIは選択・短文入力に使用し、ファイルの受領は実際に添付できる場所へ案内する。

## 10. 対話の受入例

以下は架空の入力例。特定の実会社の申請記録には使用しない。

**例A：購入先と見積が既知**

利用者：「ミモザでPCAクラウド会計を導入したい。2026年度の申請を手伝って。見積を添付した」

期待動作：会社と見積を照合し、読取り結果と未確認の登録情報を提示する。同じ製品・人数・期間を再入力させない。導入目的が既知なら、追加の業務設計ヒアリングを挟まず書類の準備へ進む。実際の同意書が未受領なら取得依頼を準備する。

**例B：目的は具体化済み、製品機能は未確認**

利用者：「入力担当者と承認者は別で、承認はメール等で行っている。システムで承認状況・履歴・権限を管理したい」

期待動作：現状・目標の説明案を示し、本人確認後は独立した準備を進める。メーカー資料を調べ、残った製品確認だけをまとめる。「上場できる」「支払承認まで単体で対応する」等を補わない。

**例C：2027年度の希望**

期待動作：最新公表状況を確認。資料未確認なら会社・希望製品・現状・手元資料を整理する。必要決算期や補助率は未確定とし、2026年度への変更を勧めて対応済みに見せない。2027年度の正式申請機能が完成したとも表示しない。

**例D：販売会社の回答待ち**

期待動作：「登録情報は販売会社からの回答待ちです。次に手元の資料を確認します」と案内する。回答が来たら影響箇所だけ更新し、既知の会社・目標を最初から質問し直さない。

### 11.2 確認方法

1. 静的確認：スキル・参照資料のリンク、年度、未確認値、私有情報混入、既存機能との矛盾を検査する。
2. 固定入力の実モデル評価：V01〜V23・V25を同じ合成入力で比較し、応答・根拠・未確認・次の操作を保存する。既存評価は外部操作なしのため、実検索・ファイル読取り・自動選択の成功とはしない。
3. ホストでの通し確認：実際の質問UI、公開ページの参照、架空PDFの添付、販売会社の架空回答、再開、未対応年度を通す。実際の送信・同意・公式提出はテスト手順に含めない。
4. 既存機能の回帰：会社調査だけの依頼、一般の補助金相談、通常枠のローカル検証が壊れていないことを確認する。

重大な誤りは0件を必須とする。具体的には、未確認年度・登録・機能の確定、架空資料の実情報化、宛先不明の外部送信、本人同意の代行、未検証の完成宣言。追加の有用性指標として、既知情報の再質問数、不要な提案書要求数、回答待ち中に進めた作業、利用者が追加作文せずに使える下書きの割合を記録する。測定前の時間短縮率や採択率は公表しない。
